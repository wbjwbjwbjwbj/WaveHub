# WaveHub 原型数据库设计草案 v0.3

依据：`docs/request.md`。本稿用于明确数据实体和讨论边界，不是最终数据库模型。
根据当前草案已提供可修改的原型建表和示例数据脚本，入口见 [`../backend/src/main/resources/db/README.md`](../backend/src/main/resources/db/README.md)。脚本字段为暂定基线，未在用户数据库执行。

## 1. 已确认的前提

- 一座台站包含多个传感器，传感器即阵元；允许选择多个台站组合计算。
- 传感器就是波形采集设备，作为同一个实体管理，统一使用 `sensor` 表保存坐标及采集参数。
- 波形由后端直接读取本机指定文件或目录，不以浏览器上传为首要流程。
- 数据库使用本机人大金仓 KingbaseES，具体版本和兼容模式待确认。
- 当前是容易变更的原型，先覆盖数据加载、台站管理、分析、测向和定位的完整链路。

## 2. 建议范围

建议先确定 **11 张核心业务表**，另有 3 张候选表按实际需求决定是否增加。
此清单不包含登录权限表；如果原型需要登录和权限管理，再单独讨论用户、角色等模型。

原始波形及体积较大的计算产物继续存为文件；数据库保存元数据、关联关系、参数快照和可检索的结果摘要。
数据格式、滤波器种类和算法参数不分别拆成大量表，避免需求变动时频繁修改表结构。

## 3. 核心表清单

| 序号 | 建议表名 | 作用 | 关键数据（尚不锁定字段类型） |
| --- | --- | --- | --- |
| 1 | `station` | 台站信息 | 台站编码、名称、经度、纬度、高程、说明 |
| 2 | `sensor` | 传感器 / 阵元 / 波形采集设备信息 | 所属台站、传感器编码、坐标、高程、类型、型号、序列号、采集能力和其他关键参数 |
| 3 | `waveform_file` | 后端本地波形文件索引 | 数据根目录标识、相对路径、格式、文件大小、修改时间、校验信息、解析状态、来源类型 |
| 4 | `waveform_trace` | 文件中的通道 / 连续波形段元数据 | 所属文件、通道标识、关联传感器、起始时刻、采样率、样本数、单位、段定位信息 |
| 5 | `source_event` | 作为推算依据的已知事件 | 事件名称、发震 / 发生时刻、经纬度、可选深度或高程、信息来源及说明 |
| 6 | `analysis_preset` | 可保存、导入、导出的分析参数方案 | 方案名称、分析类型、参数内容、参数结构版本、说明 |
| 7 | `analysis_task` | 一次分析执行记录 | 类型、状态、参数快照、引用方案、可选事件、执行时间、算法版本、错误摘要、产物位置 |
| 8 | `analysis_task_input` | 一次计算实际使用的波形输入 | 任务、波形段、传感器、样本区间、输入元数据快照 |
| 9 | `direction_result` | 信号检测和测向结果摘要 | 所属任务、信号时段、代表时刻、方向角、视速度、质量指标、参考位置快照 |
| 10 | `localization_result` | 交叉定位结果 | 所属任务、定位坐标、可选关联事件、质量或不确定性摘要、结果状态 |
| 11 | `localization_input` | 定位采用的测向结果 | 定位结果、测向结果、可选权重及输入快照 |

### 3.1 台站与传感器（波形采集设备）

- `station` 一对多 `sensor`；传感器、阵元和波形采集设备在本项目中指同一个实体。
- `sensor` 统一保存位置、型号、序列号、采集能力及其他关键参数，不另建采集设备表，也不增加传感器与采集设备之间的关联字段。
- 传感器自身保存坐标，不能只保存台站中心坐标；台站中心与阵元位置是不同数据。
- 采样率等信息需要区分“设备标称 / 配置参数”和“文件解析出的实际参数”，不能相互覆盖。
- 传感器的少量稳定字段单独建列，尚未明确的厂家参数放入带版本号的扩展参数对象。
- 批量导入导出是以上表的读写功能，暂不为它额外建立业务表。
- 传感器支持哪些通道及如何匹配文件内通道仍需讨论；如后续需要传感器换装或参数变更历史，再考虑增加历史记录表。

### 3.2 波形文件与通道 / 波形段

- `waveform_file` 一对多 `waveform_trace`，不能假设一个文件只对应一个传感器或一个通道。
- `waveform_trace` 建议以一个可独立读取的连续波形段为索引单位；同一通道有时间间断时允许对应多行。段定位信息由各格式解析器解释，不强制等同于文件字节偏移。
- 格式使用统一标识，如 `MINISEED`、`CD11`、`WAV`、`CUSTOM`，具体解析器及其版本随导入记录保存，不给每种格式单独建表。
- 实际文件路径由配置中的数据根目录和表内相对路径共同确定；界面或记录中的路径必须在后端确认的可读目录范围内解析。
- 后端索引文件后不修改原始波形。文件移动、缺失或内容变化时记录相应状态，不继续把旧元数据视为有效数据。
- 文件可先进入“待匹配 / 待补元数据”状态。通道与传感器的映射未确认时允许为空，但不能直接进入要求阵元位置的计算。
- 对没有绝对起始时刻或物理单位的输入，允许相应字段为空，并在分析前要求补齐所需信息；不能根据扩展名直接假定其时间基准。
- 滤波等处理产生的新波形也可登记为文件及波形段，通过 `created_by_task_id` 关联来源任务，并区分原始与派生文件。
- 不将每个采样点作为一行写入数据库，不将全部原始数据以 Base64 塞入参数字段。

### 3.3 已知事件与到达时段推算

- `source_event` 表示用户录入或导入、作为计算依据的事件，和系统推算出的定位结果分开保存。
- 推算功能需要事件、目标台站以及传播模型 / 速度等参数。需求尚未指定模型，当前不把某个模型和固定传播速度写死到字段中。
- 到达方向和时段可先按需计算并返回前端，不强制保存每次预测，因此核心清单不包含预测结果表。
- 如果需要保存预测、重复对比或作为后续选波依据，再增加候选表 `arrival_prediction`。
- 深度与高程的含义、单位和正负方向在字段落地前单独约定。

### 3.4 参数方案与任务记录

- `analysis_preset` 保存可复用的方案；建议类型先区分滤波、时频分析、WinPMCC、交叉定位和到达预测。
- 参数对象保存滤波器类型、带宽、加窗类型、FFT 窗口以及 WinPMCC 参数；具体字段需结合算法实际接口再讨论，不预先虚构全部参数。
- 一项方案只对应一种分析类型。需要多步骤串联时由多项任务及产物关联表达，不把执行流程和可复用方案混为一体。
- 允许参数结构随原型演化，但必须有 `schema_version`，由后端根据类型和版本校验必填项、范围及单位。
- 参数可先以 JSON 文本保存；是否使用 KingbaseES 原生 JSON 类型，在确认本机版本和兼容模式后决定。
- `analysis_task` 表示执行记录，不意味着必须建设消息队列或分布式调度。原型可以同步执行并记录状态。
- 每次执行保存完整参数快照，不能只关联可编辑方案，否则方案修改后无法解释历史结果。
- `analysis_task_input` 保存实际选中的波形段、阵元及样本区间。样本区间建议采用从 0 开始的左闭右开区间，并记录本次使用的采样率、时刻与坐标快照。
- “全阵元”是选择策略。执行前展开为具体输入行；后续台站配置变化不应改变已有任务的实际输入。
- 原型暂约定一次 WinPMCC 任务对应一个计算组合，该组合可以来自一个台站的全部阵元，也可以来自多个台站选中的阵元。
- 跨台站组合的几何参考位置、阵元选择规则仍需讨论，不能把组合结果简单归属到其中某个台站。
- 任务过程可先保存进度、开始 / 结束时间和产物路径。若仅需运行中的实时进度，可由接口推送，不按每帧建立永久记录。

### 3.5 检测、测向和交叉定位

- `direction_result` 暂合并检测与测向摘要，避免原型初期建立一整套未明确的检测对象体系。
- 一次 WinPMCC 任务可以产生多个信号时段的结果。先保存供列表、雷达图、定位选取使用的结果摘要，详细时间 / 频率网格另存产物文件。
- 方向角需要明确表示“指向信号来源”还是“信号传播方向”、角度零点及旋转方向；视速度需要明确单位。
- 结果记录参考位置快照；参与的台站与阵元可从所属任务的输入记录获得。跨站组合不能只保存一个非空 `station_id` 代替完整输入。
- `localization_result` 与 `direction_result` 通过 `localization_input` 关联，明确定位到底采用了哪些测向结果，而非只保存一个经纬度。
- 定位前应校验输入结果的时段、参考位置和方向约定是否可共同用于计算；具体信号关联规则待讨论。
- 原型先将一次交叉定位任务与相应结果关联。如果需要保留多个候选点，可在同一任务下保存多条定位结果。
- 地图图层、雷达图、波形图、时频图和时间轴联动属于展示功能，不能仅因为有一个页面就建立一张业务表。

## 4. 按需增加的候选表

| 候选表 | 何时需要 | 主要内容 |
| --- | --- | --- |
| `arrival_prediction` | 需要保存和对比事件到站预测 | 事件、台站、模型参数快照、预测方向、到达起止时刻、计算版本 |
| `display_preset` | 需要重启后恢复或导入导出展示布局 | 展示项、图表组合、联动分组、缩放及地图配置、结构版本 |
| `waveform_format_definition` | 用户需要在界面中配置自定义格式，而非开发者编写解析器 | 格式名称、字段映射、采样 / 时间 / 单位规则、解析器标识、结构版本 |

自定义格式若采用代码插件，可先由解析器及配置文件支持；若要求任意二进制格式可视化定义，需先讨论其表达能力，不能仅靠一张表保证支持。

## 5. 需求覆盖关系

| request.md 条目 | 对应实体或处理方式 |
| --- | --- |
| 1、本地文件加载与处理 | `waveform_file`、`waveform_trace`、`analysis_task`、`analysis_task_input` |
| 2、多格式及自定义格式 | 文件格式标识、解析器；必要时增加格式定义表 |
| 3、台站 / 阵元 / 采集设备管理 | `station`、`sensor`；传感器即采集设备，批量导入导出直接操作这两类实体 |
| 4、基于已知事件的到达推算 | `source_event`；预测先按需计算，可选保存 `arrival_prediction` |
| 5、多维展示、联动和缩放 | 波形 / 任务产物支持展示；临时界面状态不入库，必要时增加 `display_preset` |
| 6、滤波及 FFT 配置 | `analysis_preset`、`analysis_task`、`analysis_task_input`，派生波形登记为文件 |
| 7、WinPMCC 参数保存与导入导出 | `analysis_preset`，任务保存不可变参数快照 |
| 8、全阵元及手选组合 | 台站 / 传感器关系，执行时展开为具体 `analysis_task_input` |
| 9、WinPMCC 过程及结果展示 | 任务状态、产物文件、`direction_result`；自定义展示持久化需求另定 |
| 10、测向交叉定位及地图 | `direction_result`、`localization_result`、`localization_input` 与台站坐标 |

## 6. 下一步需要讨论

1. 实际波形样例：每种格式的通道、时间、采样率和单位来自哪里？文件通道如何匹配到传感器？
2. 台站和传感器（即采集设备）的必填参数，以及坐标参考系、坐标精度、传感器与波形通道的对应规则。
3. WinPMCC 的实际接入方式、完整参数接口、输出结构，以及跨台站组合是否作为同一个阵列处理。
4. 到达时段采用何种传播模型，方向角、视速度、深度 / 高程等量的约定。
5. 检测结果如何归为同一信号、如何选择用于交叉定位的结果，以及是否需要人工确认 / 编辑。
6. 需要保存哪些内容供重启后恢复：波形选段、分析历史、预测、图表布局、自定义展示配置。
7. 原型是否需要登录权限、多用户隔离，以及数据和结果的保留 / 删除规则。

在这些问题收敛前，脚本中的字段、约束、索引及单位约定均可继续讨论调整，算法参数结构尚未定稿。当前只生成文件，不连接数据库执行变更。
